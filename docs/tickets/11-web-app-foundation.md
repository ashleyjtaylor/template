# 11 — `apps/web` foundation: customer SPA scaffold + auth flows + accept-invite

Plan agreed via `/pre-feature` before implementation begins.
To be shipped via `feat/web-app-foundation`.

First customer-facing SPA in the template. Mirrors `apps/internal` (Vite + TanStack Router + Tailwind 4 + shadcn/ui), uses cookie-based better-auth sessions, and fills the gap left by ticket 10's invitation-create endpoint — the `/accept-invite?token=…` link returned by the API now points at a real page.

## Requirements

- **Two signup paths** are exposed in the SPA, mirroring the API design:
  - `/signup` — calls `POST /api/auth/sign-up/email` (standard, user only). Single-user-product fork default.
  - `/team-signup` — calls `POST /api/orgs/sign-up` (composite — user + organisation + owner membership in one transaction). Team-product fork default.
- **`/accept-invite?token=…`** renders the invitation preview (public via `GET /api/invitations/:token`) and, with a session whose email matches, accepts via `POST /api/invitations/:token/accept`.
- **Auth gate** — single `__root.tsx` runs `useSession()` and either renders the sidebar layout (authed) or redirects to `/login` (unauthed, except on `/login` / `/signup` / `/team-signup` / `/accept-invite`). Visiting `/login` while authed redirects to `/`.
- **Layout** — full sidebar matching `apps/internal`: brand wordmark, nav items (Home only today), env+SHA badge, user menu (signed-in-as email, theme dropdown, sign-out). No staff role pill (this isn't the staff app).
- **No personal-org-on-signup auto-create anywhere.** Standard signup yields an authenticated user with zero memberships; that's a real state and `apps/web` accepts it (the placeholder home reads "Welcome, {firstname}" and shows a TBD card — no per-org content).

**"Done" bar:**

1. Local: `pnpm dev` runs API + SPA. Standard signup at `/signup` creates a user only; team signup at `/team-signup` creates user + org + owner membership; both redirect to `/` post-success. `/login` signs in; `/accept-invite?token=<known>` renders preview and (with matching email session) successfully accepts.
2. Staging: deployed CloudFront URL serves the SPA shell; the four public auth flows behave the same as locally; smoke step in `deploy-staging.yml` curls the new URL and asserts `id="root"`.
3. Sidebar shows env badge (`staging · {sha8}` on staging) and signed-in-as email; theme switcher persists across reloads; sign-out POSTs `/api/auth/sign-out` and redirects to `/login`.

## Routes (frontend)

| Path | Auth | Calls |
|---|---|---|
| `/login` | public | `POST /api/auth/sign-in/email` |
| `/signup` | public | `POST /api/auth/sign-up/email` |
| `/team-signup` | public | `POST /api/orgs/sign-up` |
| `/accept-invite?token=…` | public preview, authed accept | `GET /api/invitations/:token`, then `POST /api/invitations/:token/accept` |
| `/` (`_authed/index`) | session | placeholder dashboard |

The `/accept-invite` page is the one auth-flow exception: preview renders without a session; the accept button is enabled only when a session exists AND `session.email === preview.email`. Otherwise the page shows "Sign in as `<email>` to accept" with a CTA that takes the user to `/login` (and back).

## Auth gate behaviour (`__root.tsx`)

Mirrors `apps/internal` line for line:

- `useSession()` returns `{ user, isAuthed, isLoading }` from `GET /api/auth/get-session` (always 200, body is `null` when unauthed).
- While `isLoading`: render nothing (avoids the login-flash).
- If authed: render `<Sidebar /> + <Outlet />`.
- If unauthed: if the current pathname is one of the public allowlist (`/login`, `/signup`, `/team-signup`, `/accept-invite`), render `<Outlet />` without chrome; otherwise navigate to `/login`.
- If authed and the pathname is `/login` / `/signup` / `/team-signup`: navigate to `/`.

No per-page 401 effects.

## Modules

### `modules/session/`

Copied from `apps/internal/src/modules/session/`. Hooks: `useSession()`, `useSignIn()`, `useSignUp()` (standard), `useSignUpTeam()` (composite — new), `useSignOut()`. The composite hook is the one new bit: `mutate({ email, password, firstname, lastname, organisationName })` → `POST /api/orgs/sign-up`. On 422 (better-auth's duplicate-email passthrough), surfaces the error to the form.

### `modules/theme/`

Verbatim copy from `apps/internal/src/modules/theme/`. `ThemeProvider` applies `dark` class to `<html>`; `useTheme()` exposes `{ theme, setTheme }` over `'light' | 'dark' | 'system'` with localStorage persistence + `prefers-color-scheme` listener for `'system'`.

### `modules/invitations/`

New. Two hooks against the existing API:

- `usePreviewInvite(token: string)` — TanStack Query wrapping `GET /api/invitations/:token`. Returns the preview shape (organisation `entityId` + name, role, email, invitedBy, expiresAt, status). 404 → query error.
- `useAcceptInvite()` — mutation wrapping `POST /api/invitations/:token/accept`. On success invalidates the session cache so the auth gate re-evaluates (in case the user wasn't yet authenticated when previewing). Errors include 403 `InvitationEmailMismatch`, 409 `Expired` / `AlreadyAccepted` / `AlreadyRevoked` — surfaced via the typed-error wire shape.

Schemas in `schemas.ts` mirror the API responses (Zod parse on read).

## Email verification

**Deferred entirely.** better-auth's `emailAndPassword.enabled` is `true` today with no `requireEmailVerification` flag, so signup yields an immediate session. No "check your email" banner, no `/verify-email` page in this PR. When SES lands its own ticket: that PR sets `requireEmailVerification: true` server-side and adds the gate UI here. Nothing in this foundation PR needs to anticipate it beyond not blocking the path.

## Infrastructure (CDK)

Mirrors the `apps/internal` SPA hosting pattern in `infra/cdk/lib/app-stack.ts`.

**AppStack changes:**

- New private S3 bucket `${PRODUCT}-${envName}-web-spa` (SSE, lifecycle rules to prune old bundles, `removalPolicy: DESTROY`, `autoDeleteObjects: true`).
- New CloudFront distribution with two origins:
  - **S3 origin** (via OAC) for `/*` — the SPA bundle. Cache hashed assets 1 year, `index.html` no-cache.
  - **ALB origin** for `/api/*` — forwards `Cookie`, `Authorization`, `Origin`; no caching.
  - Custom error response: 404 from S3 → return `index.html` 200 (SPA routing).
- API container env updates:
  - `CORS_ORIGINS` adds the new web SPA URL alongside the existing `${INTERNAL_SPA_URL}`.
  - `BETTER_AUTH_URL` stays unchanged — single value, points at one canonical app host. Two SPAs sharing one API both ride the same auth callbacks; the cookie's `Domain` (when DNS lands) makes that work cleanly. Until then, both CloudFront URLs hitting the same `/api/*` is enough.
- New CFN outputs: `WebSpaUrl`, `WebSpaBucketName`.

**No new** RDS, Redis, secrets, security groups, ECS resources, NAT changes.

**Cost delta:** ~$1-2/mo (CloudFront free tier covers our scale; S3 storage is pennies).

## CI/CD

`.github/workflows/ci.yml`:

- Existing `ci` job already runs lint/typecheck/test repo-wide (Turbo) — `apps/web` automatically picked up once `package.json` lands.
- **New `build-web-app` job** (PR-only sanity, parallels `build-internal-app`): `pnpm --filter @template/web build`, fails the PR on bundle breakage.

`.github/workflows/deploy-staging.yml`:

- **New `build-web-app` job** running in parallel with `build-internal-app` and `build-api-image`. Uploads `apps/web/dist/` as a workflow artifact.
- **New `deploy-web-spa` job** sequenced after `deploy-app-stack` (so the distribution exists): downloads the artifact, two-pass S3 sync (long-cache + immutable for hashed assets, no-cache for `index.html`), invalidates `/` + `/index.html` on the new CloudFront distribution.
- **Smoke step** extended to also `curl` the new web SPA CloudFront URL and assert the response contains `id="root"`. The existing API smoke (assert `version` matches SHA on `/health`) and internal SPA smoke remain.

No new secrets needed (OIDC role + AWS credentials reused). No Dockerfile changes (no API image change). No migration changes (no schema delta).

## Testing

**Unit** (`apps/web/test/unit/modules/theme/provider.test.ts`):

Same three tests as `apps/internal` — initial value follows `prefers-color-scheme` when localStorage is empty; `setTheme('system')` listens to live `matchMedia` change events; `setTheme('light')` / `setTheme('dark')` ignore OS changes.

**No SPA-side integration / Playwright tests in this PR.** The PR-time `build-web-app` job covers compilation; the deploy smoke covers "the bundle is being served". The API-side integration tests (already shipped by ticket 10) cover the endpoints `apps/web` calls. Manual click-through covers SPA wiring until a Playwright surface lands (next time it's worth its keep — likely when there's a real per-org feature or the email/SES work).

External I/O: the unit theme test uses jsdom + a stubbed `matchMedia`. No HTTP / DB / fetch in unit tests.
